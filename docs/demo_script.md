# 5 分钟演示脚本

> 目标：让评审在 5 分钟内看到"检索质量可度量、失败可观察"，而不是只看一次问答。

## 0:00 - 0:30 定位

打开 README 的架构图，一句话说明：

"这是一个铁路标准问答系统。标准号、限值这类精确信息靠 BM25，口语化提问靠向量检索，两路用 RRF 融合后再重排；检索结果不可信时，CRAG 的评估器会触发知识提炼或联网纠错。"

强调边界：没有 API Key 也能跑完整链路，用确定性哈希向量和词面评估器，便于复现。

## 0:30 - 1:30 建索引

```bash
python -m src.main ingest --file data/railway_standard_guide.md --reset
python -m src.main stats
```

讲解 `stats` 输出：

- `chunks`：切分后的片段数；
- `embedding.backend`：当前向量后端，`hashing-512` 表示离线基线；
- `rrf_k` / `candidate_pool`：融合与重排参数。

指出切分器做了两件容易被忽略的事：删除图床 base64（否则附录会变成一个巨大片段），超长小节按段落装箱并保留 `part/parts`。

## 1:30 - 3:00 三个问题，三种路径

```bash
python -m src.main chat --query "时速350公里路段的最小曲线半径是多少？"
python -m src.main chat --query "列车跑太快会不会撞到隧道壁？"
python -m src.main chat --query "2050 年火星铁路的建设标准是什么？"
```

逐个说明：

1. **精确查询**：BM25 命中 `TB 10621`，评估器判 Correct，走知识提炼，回答带章节来源。
2. **口语化查询**：词面命中有限，评估器判 Ambiguous，先提炼再补一次联网搜索（未配置 Tavily 时跳过），回答会明确说明依据不足。
3. **知识库外问题**：评估器判 Incorrect，没有硬编答案，而是承认"知识库中没有相关标准"。

这一段的重点是：**系统在不知道的时候会说不知道**，而不是让模型自由发挥。

## 3:00 - 4:00 检索消融

```bash
python scripts/eval_retrieval.py --top-k 1
```

解释表格：

- k=5 时三种配置都饱和，说明小语料上召回不是瓶颈，不要用 k=5 的表格假装消融有效；
- k=1 时纯向量漏 1 条，混合检索把它补回来；
- 重排在这套评测上没有带来提升，只增加约 3.5ms —— 把这一点讲出来，比声称"加了重排就更好"更可信；它的价值在"泛化章节 vs 带标准号的章节"这类排序冲突，单元测试有覆盖。

再打开 `.github/workflows/ci.yml`：单元测试 + 建索引 + `--min-hit-rate 0.95` 的检索门槛，检索退化会直接让 CI 红。

## 4:00 - 5:00 工程细节

打开 `src/rag/retriever.py` 的降级分支，说明三件事：

1. 向量腿失败时回退 BM25，`vector_error` 写进 trace、日志和 UI，不静默；
2. 同一来源重复入库先删旧片段，chunk id 由内容哈希生成，重跑不会产生重复；
3. 索引维度与当前 embedding 后端不一致时直接报错，并提示用 `--reset` 重建。

收尾："这个项目的重点不是把 RAG 串起来，而是让检索层的每个决策都有参数、有指标、有失败路径。"
